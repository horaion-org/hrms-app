# Spec: Horaion icons and Sidebar

Status: ready-for-agent

## Problem Statement

Horaion's design has a main navigation Sidebar: a full-height Ink Blue rail with the Horaion logo at the top and one item per Module (Dashboard, Scheduling, Leave, People, Organisation). Each item has three visual states: default, hover and active. None of this exists in the codebase. There is no layout component, no navigation component and no app shell, so every Module that gets built later has nowhere consistent to be reached from.

The design also has its own icon set of 77 icons, including outline and filled pairs for every Module. The Sidebar depends on them because an active item swaps its outline icon for the filled one. The codebase only has Heroicons, which has no match for the Leave icon (a clock with an arrow) or the Organisation icon (an org chart), and doesn't match the design's strokes for the rest. Right now a developer who needs a design icon has to copy SVG paths out of the design by hand, one at a time.

## Solution

Two new building blocks, both usable from Storybook and ready to be wired into the app later:

1. **Horaion icons.** Every icon in the design's icon sheet becomes a React component, all generated by a script from the committed sheet. Each icon is drawn once on a 24px grid, takes its colour from the surrounding text colour, and scales to any size. The design's 16, 24 and 32px sizes are exact scales of each other, so one drawing covers all three. The icons sit alongside Heroicons without replacing them.
2. **Sidebar.** A layout component that draws the rail, the Horaion logo (linking home) and a flat list of Sidebar items. A Sidebar item is a router link, and the router decides whether it's active. An active item gets the light Ink Blue fill and its filled icon.

Connecting the Sidebar to real Module routes is a follow-up. This spec delivers the components, their stories and their tests.

## User Stories

### Icons

1. As a developer, I want every icon in the design's icon sheet available as a named React component, so that I never copy SVG paths out of the design by hand.
2. As a developer, I want icon names that match the design's labels (e.g. the design's "leave-filled" is `LeaveFilledIcon`), so that designers and developers use the same words.
3. As a developer, I want the Module icons in outline and filled pairs (Dashboard, Scheduling, Leave, People, Organisation), so that I can show inactive and active states.
4. As a developer, I want icons to take `currentColor` for stroke and fill, so that I colour them with ordinary text colour utilities such as `text-ink-blue-900`.
5. As a developer, I want each icon to scale cleanly to any size through CSS, so that one component serves the design's 16, 24 and 32px sizes and in-between sizes such as the Sidebar's 20px.
6. As a developer, I want Horaion icons to accept the same props as Heroicons, so that I can pass either kind anywhere an icon is expected (e.g. the Button's leading and trailing icons) without adapters.
7. As a developer, I want Horaion icons imported from their own module path, so that the import line shows whether an icon is a Horaion icon or a Heroicon even when the names overlap.
8. As a developer, I want Heroicons to keep working, so that existing code and icons missing from the design's set are unaffected.
9. As a developer, I want importing one icon to add only that icon to the bundle, so that the icon set doesn't bloat every page.
10. As a developer, I want to regenerate every icon component by running one script after the design sheet is re-exported, so that icon changes in the design reach the code in one step.
11. As a developer, I want the generator's output to be deterministic, so that regenerating unchanged input produces no diff.
12. As a designer, I want to see every icon in one Storybook gallery with its name, so that I can check the code against the design at a glance.
13. As a screen-reader user, I want decorative icons hidden from assistive technology, so that I don't hear meaningless graphics announced.
14. As a screen-reader user, I want an icon given a title to be announced as an image with that name, so that icon-only controls still make sense.

### Sidebar

15. As a user, I want a navigation rail down the left of the app, so that I can reach every Module from anywhere.
16. As a user, I want the Horaion logo at the top of the rail, so that I always know which product I'm in.
17. As a user, I want clicking the Horaion logo to take me to the Dashboard, so that I have a quick way home.
18. As a user, I want each Module shown as an icon plus a label, so that I can recognise it quickly.
19. As a user, I want the item for the Module I'm in to be highlighted with a light fill and a filled icon, so that I always know where I am.
20. As a user, I want an item to darken when I hover over it, so that I know it can be clicked.
21. As a user, I want clicking an item to take me to that Module, so that I can move around the product.
22. As a keyboard user, I want to tab through the logo and every item in order, so that I can navigate without a mouse.
23. As a keyboard user, I want a clearly visible focus ring on the focused item, even on the dark rail and on the light active item, so that I always know where keyboard focus is.
24. As a keyboard user, I want to activate an item with Enter, so that links behave as expected.
25. As a screen-reader user, I want the Sidebar exposed as a navigation landmark, so that I can jump to it directly.
26. As a screen-reader user, I want the active item announced as the current page, so that I know where I am without seeing the highlight.
27. As a screen-reader user, I want items announced by their text label only, so that the icon doesn't add noise.
28. As a user, I want items to behave as real links (open in a new tab, copy link address), so that the Sidebar works like the rest of the web.
29. As a developer, I want the Sidebar to take its items as children instead of a hard-coded Module list, so that it can be reused and tested with any items.
30. As a developer, I want a Sidebar item to take a route, a label, an outline icon and an active icon, so that adding a Module to the navigation is a single declaration.
31. As a developer, I want the router to decide which item is active, so that the highlight can never fall out of sync with the URL.
32. As a developer, I want Sidebar and Sidebar item stories showing each state and the full five-Module layout from the design, so that I can review them without running the app.
33. As a developer, I want every colour class the Sidebar uses to be checked against the real stylesheet, so that a misspelled or undefined colour token fails a test instead of shipping silently.

## Implementation Decisions

### Icon module

- **One component per icon, named exports.** Each icon is a named export called `<PascalName>Icon`, taken from the design's label. `leave-filled` becomes `LeaveFilledIcon`, `ai` becomes `AiIcon`, `more-vertical` becomes `MoreVerticalIcon`. There is no single `<Icon name>` component. That keeps imports tree-shakeable and makes names type-checked.
- **Signature.** Every icon uses the existing shared `Heroicon` type from the common types module, so either kind of icon fits wherever the other does. Props (including `className` and `title`) reach the root `<svg>`.
- **Accessibility.** With no `title`, the SVG is `aria-hidden="true"`. With a `title`, it renders a `<title>`, sets `role="img"`, and connects the two through `aria-labelledby` (using `titleId` if given, otherwise a generated id). This matches how Heroicons behaves.
- **Geometry.** Every icon has `viewBox="0 0 24 24"` and is drawn from the 24px column of the sheet (stroke width 1.5, round caps and joins as in the source). The 16px and 32px columns are exact 2/3 and 4/3 scales with proportionally scaled strokes, so they aren't extracted. The default rendered size comes from CSS (`size-*` utilities). The SVG has no fixed width or height beyond what Heroicons would set.
- **Colour.** Every hard-coded colour in the source (`#2E2F33` on both `stroke` and `fill`) becomes `currentColor`. Elements with `fill="none"` keep it.
- **Coexistence with Heroicons.** Heroicons stays a dependency. Horaion icons always come from the Icon module's barrel and Heroicons from its own package. Import sites tell them apart by import path. Names aren't prefixed, and the rare file that uses both aliases one of the two.
- **Location.** The Icon module is a UI primitive under the shared UI components area, following the repo's component folder conventions (component, stories, test, barrel). The generated icon components sit together inside that folder, and one gallery story and one test cover the whole set instead of a quad per icon.

### Icon generator

- **Input.** The design's icon sheet is committed to the repo next to the generator as the single source of truth. It's a 2560×1256 sheet with six column groups of up to 15 rows on an 80px grid. Each group holds a 16px, a 24px and a 32px copy of an icon plus its label.
- **Name manifest.** The labels in the sheet are outlined paths, not text, so they can't be read automatically. A hand-written manifest maps each grid cell (group and row) to its design name. It lists all 77 icons in sheet order:
  - Group 1: placeholder, notification, chevron-left, chevron-right, chevron-up, chevron-down, plus, minus, view, dashboard, scheduling, leave, people, organisation, menu
  - Group 2: arrow-left, arrow-right, arrow-up, arrow-down, tick-filled, cross-filled, alert, system, generate-schedule, add-staff, approve-requests, fill-shifts, dashboard-filled, scheduling-filled, leave-filled
  - Group 3: people-filled, organisation-filled, settings, filter, close, search, grid, list, edit, more-vertical, history, publish, time, break, role
  - Group 4: location, swap, copy, delete, info, checkbox, checkbox-filled, sort, medium, radio, radio-filled, table, tick, cross, alert-filled
  - Group 5: warning, save, ai, attachment, upload, download, phone, email, remove-user, user, notes, skills, permissions, department, checkbox-half
  - Group 6: camera, info-filled
- **Process.** The generator parses the sheet and assigns each `<path>` and `<circle>` to a grid cell by its position. For each manifest entry it keeps the 24px copy's elements and translates them so the icon sits in a 0 0 24 24 box. It swaps colours for `currentColor` and writes one component per icon plus the barrel's exports. Labels and the white background rectangle are dropped.
- **Determinism.** Output is formatted with the repo's Prettier config and ordered by manifest, so unchanged input gives byte-identical output. The generated files are committed and marked as generated at the top, so nobody hand-edits them.
- **Invocation.** It's exposed as a package script so that regenerating is one command.

### Sidebar module

- **Structure.** It sits in the shared layout area as nested component folders, following the layout README's pattern: a Sidebar and a Sidebar item, each with the full component quad, plus a barrel. There's no Sidebar section. The design has one flat list, so grouping waits until a design calls for it.
- **Sidebar interface.** It takes `children` (the items) and an optional `className`. It renders:
  - a full-height rail 280px wide with an `ink-blue-900` background
  - the Horaion logo at the top, as a router link to `/`, with an accessible name
  - a `<nav>` landmark with an accessible label, containing a list of the children
  - no Module list of its own. The Sidebar knows nothing about Modules.
- **Sidebar item interface.** It takes `to` (a registered route, typed through TanStack Router's link props), `label`, `icon` and `activeIcon` (both `Heroicon`-typed components, so Horaion icons or Heroicons both work), and passes any other link props through.
- **Active state comes from the router.** A Sidebar item renders TanStack Router's `Link`. The router's active matching decides the state and sets `aria-current="page"`. The item uses the router's active status to choose between `icon` and `activeIcon`. No caller passes an `active` flag.
- **Visual states** (colour tokens from the colour-tokens spec):
  - **Default:** transparent background, white label, outline icon in white.
  - **Hover:** `ink-blue-800` background, white label, outline icon.
  - **Active:** `ink-blue-100` background, `neutral-900` label, filled icon in `ink-blue-900`. Hovering over the active item doesn't change it.
  - **Focus-visible:** a 2px white outline with an offset, on every state.
- **Dimensions** (measured from the design mockup, which wins if anything disagrees): items are 224×48 with slightly rounded corners, 16px inner padding, a 20px icon, a 12px gap between icon and label, 16px label text and 16px vertical spacing between items. The rail has 28px horizontal padding. The logo is about 40px and sits above the list, 28px from the top.
- **Icons are decorative inside items.** The item's accessible name is its label. The icon stays `aria-hidden`.
- **Logo.** The real Horaion logo asset isn't available yet. The implementer recreates the pie-chart mark from the mockup (a pie with one quarter pulled out, filled `ink-blue-100`) as a separate logo component, so swapping in the real logo later only touches that one component.
- **Glossary.** The five destinations are **Modules** as defined in the project glossary. Use that word in code, stories and comments instead of "section", "area" or "page".

## Testing Decisions

- **What a good test looks like.** It checks what a user or consumer can see: roles, accessible names, `aria-current`, which icon shows, where a click goes, and which CSS a class produces. It doesn't check component internals, class-string order or markup nesting beyond what accessibility needs.
- **Seam 1: the Icon module's barrel.** A Testing Library test imports the barrel and runs through the name manifest. It checks that:
  - every manifest name has a matching `<PascalName>Icon` export
  - each one renders an SVG with `viewBox="0 0 24 24"` and at least one drawn element, and no hard-coded colour other than `currentColor` or `none`
  - with no `title`, the SVG is `aria-hidden`
  - with a `title`, it can be found by `role="img"` and that accessible name
  - `className` reaches the SVG
- **Seam 2: the Sidebar in an in-memory TanStack router.** This is the main behavioural seam and the only new kind of seam. Tests build a small router with memory history and sample routes, render a Sidebar containing sample Sidebar items, and check that:
  - there's a navigation landmark with its label
  - the item matching the current location has `aria-current="page"` and shows its active icon, and the others have neither
  - clicking another item navigates and moves the active state
  - the logo is a link to `/` with an accessible name
  - items can be reached by keyboard in order
- **Sidebar item test.** The component conventions require one. It covers what's specific to a single item through the same router harness: the label is the accessible name, the icon is hidden from assistive technology, and extra link props pass through.
- **Seam 3: the existing compiled-stylesheet test.** It already compiles the app's real Tailwind entry and checks that the Button's colour classes produce CSS. It gets extended so every colour class the Sidebar and Sidebar item use also produces CSS. This isn't a new seam.
- **Generator.** It's covered through its output: the barrel test in seam 1 fails if the generator drops or misnames an icon. Running the generator a second time without changing the sheet must leave the working tree clean. The implementer checks this, and it doesn't need its own test.
- **Stories.** They're Storybook stories only, not run as tests:
  - an Icons gallery with every icon and its name
  - Sidebar item stories for default, hover (via the pseudo-state or a forced class) and active
  - a Sidebar story that recreates the design's five-Module layout, with one story per active Module
  - stories use the same in-memory router approach as the tests
- **Prior art.** The Button's Testing Library suite is the model for structure and naming. The compiled-stylesheet test is the model for seam 3. No router-wrapped component test exists yet, so seam 2 sets that pattern.
- **Gates.** `pnpm lint` (zero warnings), `pnpm test:unit` and `pnpm build` must all pass.

## Out of Scope

- The app shell or root layout that places the Sidebar next to page content.
- Routes and pages for the five Modules. When the wiring happens, the Dashboard Module lives at `/` and replaces the boilerplate Home page.
- The five-Module navigation config (label key, route, icons). It needs registered routes to type-check, so it comes with the wiring.
- i18n keys for Module labels. Stories and tests use literal sample labels.
- End-to-end tests of navigation in the running app.
- Collapsing to an icons-only rail, a mobile drawer or any responsive behaviour. The Sidebar is a fixed-width desktop rail.
- Showing or hiding Modules by role or permission. Every user sees every item passed in.
- Sidebar sections or grouping.
- Moving existing Heroicons uses over to Horaion icons, or removing the Heroicons dependency.
- The final Horaion logo artwork.
