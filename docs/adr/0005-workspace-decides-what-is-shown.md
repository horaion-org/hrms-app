# The workspace decides what is shown; the API decides what is allowed

Status: Proposed — Moses is asked to accept this decision in the PR before merge.

The app shows, hides and disables navigation entries and controls from one source: the permission keys in `GET /api/v1/me/workspace`, read through `useAccess` and `<Can>` in `features/workspace` (originally `useCan` and `useCanAnywhere`; see the 2026-10-09 amendment). A grant reaches everything beneath it, so a key held at the company applies at every Branch and Department, and a key held at a Branch applies at its Departments; the API applies this when it builds the workspace, and the app reads each node as sent. A Module is offered in the Sidebar when any of its read keys is held at any scope. This follows API ADR-0022, where the workspace is the shadow of a person's grant scopes.

This is a courtesy to the person, not a control. Nothing in the browser is trusted: the API checks every request, and a control shown by mistake still ends in a 403. For that reason the keys are never stored outside the in-memory query cache, and no route or component treats "the workspace says yes" as permission to skip a request's own failure handling.

We rejected deriving visibility from role names, which would duplicate the API's role-to-permission mapping in the app and drift from it. We also rejected decoding permissions from the access pass: grants are scoped to units and change without a new Session.

## Consequences

The workspace can be out of date when grants change during a Session. Any 403 from the API, other than a revoked membership (which the Session wiring handles) or the workspace request itself, reloads the workspace, so a control the person should no longer see disappears after the first refusal instead of staying until the next sign-in.

Until the workspace has loaded, every answer is "no": controls appear once it arrives, and never flash and vanish.

Permission keys are a typed list in `features/workspace/permissionKeys.ts` mirroring the API's catalog. A key the API adds must be added there before the app can gate on it; an unknown key in a response is harmless.

The company-wide lists of Branches, Departments and Job titles are filtered by the API to the units where the person holds the list's read key (API ADR-0037), so the app shows such a list whenever the key is held anywhere in the company and never trims rows itself. A row the API returns is one the person may read. System roles and the activity feed have no unit and still need their key at company level. (Amended 2026-10-06; before this, these lists were hidden unless the key was held at company level.)

## Amended 2026-10-09: explicit targets, one index, bounded freshness

Following the permissions-and-scopes review (API `docs/implementation/2026-10-09-permissions-and-scope-review.md`, §9.3–9.5, §11), four things change. The principle above stands: the workspace decides what is shown, the API decides what is allowed.

**The API's inheritance is the only inheritance.** Each workspace node already carries its effective permissions: the API's workspace rule puts company grants on every Branch and Department and Branch grants on their Departments. The app no longer merges parent lists again (the old `permissionsAt`). A question names its target explicitly as a `ScopeRef` (`{ kind: "company" }`, a Branch or a Department; `recordScope(departmentId)` for a member's records, which are at the company when they have no Department), and is answered from that node's own set. A unit the workspace does not list answers no; it never falls back to the company, so a missing or mistyped id can only hide a control, never widen one.

**One lookup, one hook.** `buildAccessIndex` turns a company of the workspace into a map from target to permission set plus the set held anywhere, memoised per workspace answer and company (`accessIndexOf`). `canAt`, `canAnywhere`, and explicit `canAny` (alternatives) and `canAll` (prerequisites) read it. `useAccess` is the one hook pages, dialogs and `<Can>` use (`useCan` and `useCanAnywhere` are gone); route loaders call the same pure functions. `<Can>` takes `permission`, `anyOf` or `allOf`, and an explicit `at` (a `ScopeRef` or `"anywhere"`), so an array of keys never silently means "any". Each row action asks its own action at the row's own target: reading a list never implies changing every row on it, and assignment changes are checked at each assignment's place, not once per grouped person. A Module is still offered when any of its read keys is held anywhere. Self-service (My profile, My leave, the colleagues directory) never asks the workspace, so it keeps working when the workspace is empty or failing, while administrative controls fail closed.

**Bounded freshness instead of forever.** The workspace query is stale after 30 s, reloaded on window focus and reconnect when stale, and polled every 60 s while the page is visible (not in the background). These are presentation intervals, not a security expiry. A reload keeps the last answer on screen until the next arrives, so gated controls do not flicker. A 403 still reloads it, except for `MEMBERSHIP_REVOKED` (the Session wiring re-settles the company and now also drops every cached query of that company, own records included) and business-rule refusals such as `OWN_LEAVE_REVIEW_DENIED`, which reloading roles cannot fix. A 404 from reading one administrative record (a person's profile) also reloads it, because the API answers 404 for a record that moved out of reach; other 404s do not.

**Administrative data is withdrawn when access shrinks.** Every query declares `meta.accessKind` (`administrative` for data reached through grants, `self` for the caller's own records and context) and its `companyId`. An access-refresh coordinator (`watchAccessChanges`, wired with the refusal listener in `connectAccess`) compares each new workspace answer's effective permission map with the previous one. When any node of a company lost a key, or disappeared, it resets that company's administrative queries (aborting their requests through the query's `AbortSignal`, which `apiRequest` passes to `fetch`) and removes them from the cache, so a late response cannot repopulate them and the next render builds a fresh query from the current grants. Administrative lists use `accessiblePreviousData()` instead of `keepPreviousData`, which never keeps a withdrawn query's rows on screen as a placeholder. Self-service queries are never withdrawn for grant changes.

### Consequences of the amendment

Test and story fixtures describe the workspace the way the API sends it (`effectiveWorkspace` in `common/testing`): a fixture that gives a key "company-wide" also lists it on every unit.

The permission catalogue is generated from the API's contract (amended 2026-10-09, second half). `contracts/permission-catalog.json` is a byte copy of the API's exported `contracts/permission-catalog.json`; `pnpm generate:permissions` validates it (schema version, key shape, `resource:action` consistency, scope values, prerequisites naming known keys without loops) and writes `features/workspace/permissionContract.generated.ts`, and `pnpm lint` runs the same script with `--check`, so a contract that changed without regeneration fails CI. `permissionKeys.ts` derives every list, guard and lookup from it, and the handwritten `permissionCatalogue.ts` and `PermissionsGrid` are gone: both role editors (the create/duplicate Dialog and the editor page) use one `PermissionChecklist`, whose ticking follows the contract's `prerequisites` and which disables a key whose prerequisite the person cannot grant, with the reason. `roleFitsScope` reads `assignableScopes`, so the assign Dialog offers only places every key of the chosen role fits and names the keys in the way when none does. A key the app does not know is never dropped: the editor shows it ticked and locked, says the app needs updating, and saves it back (ADR-0006); gates simply ignore it. All of this is presentation; the API still validates prerequisites, scope compatibility and known keys on every request.
