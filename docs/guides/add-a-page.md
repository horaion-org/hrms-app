# Add a page

A signed-in page with its own address, a menu entry for the people who may open it, and a test that opens the real
app at that address. Below, `<name>` is the address (`timesheet`), `<Name>` the page (`Timesheet`) and `<feature>` the
folder under `src/features` that owns what the page shows.

## Steps

1. **Choose the keys that open the page.** In `src/features/workspace/permissionKeys.ts`, use the `*_READ_KEYS` list
   that fits, or add one beside `REPORT_READ_KEYS`: a `ReadonlyArray<PermissionKey>` with a docstring saying where it
   is held. A key the contract does not have yet: follow [Add a permission key](add-a-permission-key.md) first.

2. **Put what the page reads and shows in `src/features/<feature>/`.** Requests, hooks and components live there, not
   in the page; see [Add an API read or write](add-an-api-read-or-write.md). A new feature folder needs nothing else
   to exist.

3. **Write the page, composition only: `src/pages/<Name>.tsx`.** A named export returning `FunctionComponent` (from
   `@/common/types`) that calls hooks, makes one pure call each, and returns JSX. Copy `src/pages/RecentActivity.tsx`:
   it reads its search through `getRouteApi("/_authenticated/_app/<name>")` and shows each state of its hook (hidden,
   error, pending, ready). Decisions go in a pure module in the feature, with a table test.

4. **Add the route: `src/routes/_authenticated._app.<name>.ts`.** Copy one of:
   - `src/routes/_authenticated._app.activity.ts` when one company-wide key opens the page: its loader sends a person
     without the key to Forbidden through `forbiddenRedirect`.
   - `src/routes/_authenticated._app.reports.ts` when the page reads per Branch or Department: its `staticData`
     shows the header's Branch choice.

   The path in `createFileRoute("/_authenticated/_app/<name>")` must match the file name.

5. **Let the router write the route tree.** `src/routeTree.gen.ts` is generated by the router's Vite plugin whenever
   Vite or Vitest starts (`pnpm dev`, `pnpm build`, `pnpm exec vitest run …`). Run step 9's test command once, then
   commit the regenerated file with the route. Never edit it by hand. Until it is regenerated, `tsc` fails on the
   route's path.

6. **Add the menu entry in `src/pages/MainLayout.tsx`.** A `<SidebarItem>` inside
   `<Can anyOf={<NAME>_READ_KEYS} at="anywhere">`, copied from the Reports entry, in the place the menu should show
   it. Then add its label to the list in `src/pages/MainLayout.test.tsx`, test "lists the entries in menu order for a
   person who holds every key", at the same place.

7. **Add the copy** ([Add copy](add-copy.md)): `shell.navigation.<name>` in both
   `src/assets/locales/en/translations.json` and `src/assets/locales/es/translations.json`, and a `<name>` section
   for the page's own words.

8. **Write the page test: `src/features/<feature>/<Name>.test.tsx`.** Copy `src/features/reports/Reports.test.tsx`:
   `stubApi` answers the API, `openApp("/<name>")` opens the real route tree, `renderAuthApp` renders it. Cover at
   least: a person holding the key sees the page; a person without it does not get the page (Forbidden, or the
   page's hidden state).

9. **Prove it.**

   ```sh
   pnpm exec vitest run --maxWorkers=3 src/pages/MainLayout.test.tsx src/features/<feature> src/common/locales.test.ts
   pnpm exec tsc --noEmit
   pnpm lint
   ```

   The menu order test fails until step 6 is done in both files. `tsc` fails while a `t("…")` key is missing from
   the English copy, and `src/common/locales.test.ts` while English and Spanish differ.
